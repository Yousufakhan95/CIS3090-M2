Performance analysis: Lecture 14 
•Speedup and eﬃciency: S = T_serial/T_parallel, E = S/p. Linear speedup S = p is ideal, 
and real results are usually worse.

•Overheads that grow with the number of threads or processes: managing threads, critical 
sections, mutex functions, network I/O, ﬁle I/O. They’re why eﬃciency usually drops as p 
grows.
•Amdahl’s law: with serial fraction a, S = 1 / ((1 - a)/p + a). As p grows, S approaches 1/a, no 
matter how many cores you add. Use it to understand the upper bound of the payoﬀ and 
choose p sensibly.
Parallel hardware and data layout: Lectures 7 and 14 
•Locality: contiguous arrays vs pointer-chasing. Looping over a ﬂat array touches 
neighbouring addresses, which gives good spatial locality.
•Transfers: one large contiguous block can be moved in one piece, as an MPI message or a 
copy to the GPU.
•Flynn’s taxonomy - SISD, SIMD, MISD, MIMD.
•Vector processors: how they work, and their beneﬁts and drawbacks.
Distributed memory programming with MPI (practicalities & patterns): 
Lectures 9-11 
•Initialization and understanding the computing environment: MPI_Init, MPI_Comm_size, 
MPI_Comm_rank.
•Matching: communicator, source, and tag must all agree. Use tags to distinguish message 
types, as in A2.
•After a receive with MPI_ANY_SOURCE, use status.MPI_SOURCE and status.MPI_TAG 
to learn the sender and the tag, and MPI_Get_count for the number of elements received 
(A2, Pacheco 3.1).
•Ordering: nonovertaking for the same sender, no global order across diﬀerent senders.
•Blocking pitfalls: a missing or mismatched send/recv can hang. If the source, tag, or 
communicator doesn’t match, the receive never completes.
•I/O: assume only rank 0 reads stdin. Printing from multiple ranks is not ordered.
•Collective communication: which ranks call a collective, and where the result ends up for 
Bcast, Reduce, and Allreduce. Typical pattern: broadcast parameters once, compute 
locally, combine with one Reduce/Allreduce. Classic send/gather pattern from our basic 
examples.
GPGPU with Warp: Lectures 15 and 18 
•GPGPU: heterogeneous computing (host and device), and the cost of copying data to and 
from the GPU.
•Design: ﬂat, contiguous buﬀers, uniform work per thread, minimize CPU-GPU transfers.
•@wp.kernel: static types, no return - write outputs to arrays.

Image processing basics: Lectures 16 and 17 
•Discrete convolution: weighted sum over an n x n neighbourhood around each pixel.
•Smoothing: kernel typically normalized (sum of all kernel weights = 1) to preserve mean 
intensity. It blurs edges while reducing noise.
•Gaussian and median ﬁltering give you more ﬁne-grained control over which high-
frequency detail is preserved.
•Unsharp masking: f_UM = f + k*g, where g is the edge image (the original minus a blurred 
version). k controls sharpening strength.
•Borders: copy of input pixels, truncation of the image, reﬂection, truncation of the kernel - 
know what each one does to the output’s size and its border pixels.
•Implementation habits: 2D-as-1D storage, contiguous arrays, avoid unnecessary copies.
Analysis of diﬀerent parallel programming approaches: Pthreads vs 
MPI vs Warp 
Memory/communication model:
•Pthreads: shared address space; synchronize with mutexes/conds/atomics.
•MPI: separate processes; message passing (point-to-point, collectives).
•Warp: separate host and device memory. Data is copied to the device, and kernels 
operate on GPU device memory.
Execution targets:
•Pthreads: threads on a shared-memory machine.
•MPI: processes across one or more nodes (CPUs).
•Warp: heterogeneous CPU host + NVIDIA GPU (or CPU fallback).

Built-in facilities:
•Pthreads: barriers (pthread_barrier_wait), DIY reductions (no collectives).
•MPI: rich collectives (Bcast, Reduce, Allreduce, Gather, …).
•Warp: kernel launches over N elements.
Best-ﬁt workloads:
•Pthreads: ﬁne-grained shared state updates (with careful synchronization).
•MPI: large independent chunks; modest communication between steps.
•Warp: large, data-parallel maps, uniform work, enough work per element to pay for the 
copies.
Common pitfalls:
•Pthreads: data races, deadlocks, oversubscription.
•MPI: mismatched tags/ranks, deadlocks, frequent small messages between machines.
•Warp: excessive host-device copies, non-contiguous data, problems too small to pay 
for the copies.

2.A manager process receives a result from any worker with 
MPI_Recv(buf, 256, MPI_CHAR, MPI_ANY_SOURCE, TAG_RESULT, MPI_COMM_WORLD, 
&status); 
The result may be shorter than 256 characters. How does the manager ﬁnd out which 
worker sent it, and how many characters it contains?
•A. It reads status.MPI_SOURCE, and calls MPI_Get_count(&status, MPI_CHAR, &n) for 
the number of characters.
•B. MPI_Recv returns the number of characters, and MPI overwrites the source 
argument with the sender’s rank.
•C. It reads status.MPI_TAG, which MPI sets to the sender’s rank, and uses sizeof(buf) 
for the number of characters.
