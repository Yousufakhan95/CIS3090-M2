•These optimizations are accompanied by lack of general-purpose GPU hardware
•GPUs often skip complex branch/control logic and cache/memory management, and

===== PAGE 11 =====
The stream programming model
•3D graphics computations - and therefore, the overall GPU architecture - are based around 
the stream programming model
•All data is represented as a stream - an ordered set of data of the same data type
•Can be simple - a stream of integers or ﬂoating-point numbers
•Can be more complex - a stream of points / triangles / transformation matrices
•We expect thousands of elements in the stream - or more!
•Operations on streams include 
•copying them
•indexing into them with a separate index stream
•performing computation on them with kernels - which is what we are most interested in
11

===== PAGE 12 =====
Kernels
•A kernel is a generic term for a small program / function that operates on elements in a stream
•This term kernel comes from mathematics, where it's used in functional analysis, linear algebra, etc.
•Also used in image processing, where a kernel represents a transformation matrix
•A kernel operates on entire streams, taking one or more streams as inputs and producing one or 
more streams as outputs
•The deﬁning characteristic of a kernel is that it operates on entire streams of elements, as 
opposed to individual elements
•The most typical use of a kernel is to evaluate a function on each element of an input stream - a 
map operation
•E.g. a transformation kernel may project each element of a stream of 3D points into a diﬀerent 3D 
coordinate system
12

===== PAGE 13 =====
Kernels
•Kernel operations include
•expansions - more than one output element is produced for each input element
•reductions - more than one element is combined into a single output element
•ﬁlters - a subset of input elements are output
•Think of individual 3D points of a model forming a stream
•Each operation in a rendering pipeline can be represented as one or more kernels
•Multiple operations could be combined into a single kernel
13

===== PAGE 14 =====
Kernels and data parallelism
•Kernel outputs are based only on their kernel inputs
•Within a kernel, you can read any element of the input arrays and write one output
•However, your output may not depend on another thread's output
•These restrictions give us a high degree of data parallelism and have two major advantages
•First, the data required for kernel execution is completely known when the kernel is written (or 
compiled)
•Kernels can thus be highly eﬃcient when their input elements and their intermediate computed 
data are stored locally or are carefully controlled global references
•Requiring independence of computation on separate stream elements within a single kernel 
allows mapping what appears to be a serial kernel calculation onto data-parallel hardware
14

===== PAGE 15 =====
Kernels and GPGPU
•GPGPU programming follows the following pattern:
•Arrange the problem so that the input data is a stream
•Write one or more kernels that operate on the stream
•If you have more than one, they have to work in sequence
•In the stream model, only one kernel can be applied to a stream at a time
•Load the data and the kernel, and run the computation

===== PAGE 25 =====
GPU and data
•GPUs are designed to have lock-step threads operate on pre-loaded data
•Anything that breaks the uniformity aﬀects performance
•Threads execute in lockstep groups
•If threads in a group take diﬀerent branches, the group runs both paths and masks oﬀ the 
inactive lanes
•The divergent code costs the sum of both branches
•So it is best to load one ﬂat data buﬀer (stream), which is then operated on by the various 
compute units and shading units (all running a single kernel)
25

===== PAGE 26 =====
Homogeneous computing 
•All examples we have seen in the course were examples of homogeneous computing - all 
execution units were of the same type (CPU cores)
•In MPI, each node on the network might be a slightly diﬀerent CPU
•However, the code is still compiled to run on all CPUs, so the CPUs must be compatible with 
each other
•Each process still runs in a CPU core, and all CPU cores would have a very similar architecture
•Otherwise the code simply won't run
•E.g. mixing Intel and AMD CPUs will be ﬁne - all are x86 compatible
•Mixing Intel and ARM CPUs will not work
26

Heterogeneous computing 
•GPGPU is an example of heterogeneous 
computing
•We start a main program on a CPU
•It loads the data (stream)
•It loads the GPU kernels (written in their own

•They are compiled before being loaded, so 
they can run on the GPU architecture
•It sends the data stream to the GPU, so 
kernels can operate on it
•Executes the kernels
•It gets the result back from the GPU

===== PAGE 28 =====
New cost
•On the surface, GPGPU looks like threading - shared memory, direct access, etc.
•Once the code and the data are on the GPU, you do indeed get direct access to the memory 
(and potential for data races), though the programming model itself is fundamentally diﬀerent
•However, it borrows from the distributed memory programming as well - on most systems, 
the CPU and GPU have their own memory spaces
•Moving the data to the GPU requires a copy over the bus, which is expensive
•In fact, it can be the dominant cost for small problems - and the reason why a naive GPU port 
might be slower than the original CPU implementation

GPGPU libraries

and API created by Nvidia
•Only runs on Nvidia GPU hardware

===== PAGE 31 =====
Nvidia Warp
•The GPGPU API used in this course is Nvidia Warp
•Free, open-source
•Developed by Nvidia
•Runs on Nvidia GPUs in parallel
•Runs on the CPU - but only as a single-thread, serial program (for now, anyway...)
•Can be used with CPU and GPU backend with identical code/semantics
•With CPU mode, you can learn GPGPU programming, though you won't get the speedup 
beneﬁts, unless you run it on compatible Nvidia hardware

===== PAGE 32 =====
Nvidia Warp
Advantages
•Hides a lot of complexities of GPGPU
•Both CPU code and kernel code are written in Python
•JIT converted to C++/CUDA and compiled at runtime
•In OpenCL or CUDA, you write 
•CPU code in C
•the kernel code - in a dedicated programming language (diﬀerent for CUDA and OpenCL)
•Simple architecture - data stream and kernels
•Don't need to deal with the complexities of multiple compute units and all the non-trivial 
communication and synchronization between them

===== PAGE 33 =====
Using Warp in 3 simple steps
•We write the GPU kernel in Python 
•We write the CPU portion in Python
•We execute the CPU code as a normal Python program (the ﬁle can contain the GPU kernel 
in it)
•Behind the scenes, Warp does the following:
•Auto-generates C/C++ code based on the CPU code, compiles it
•Auto-generates CUDA code based on the GPU code, compiles it
•Executes the CPU code, which executes the GPU kernel and manages all the data transfer 
between the CPU and the GPU

Warp example 1: adding two arrays

•Internally, the kernel function will need to know its unique ID - just like a Pthread function or 
an MPI process - called thread index in Warp
•We get it with the function wp.tid(): 
tid = wp.tid() 
•We can then do the addition - each individual call to the kernel function adds the two

z[tid] = x[tid]+y[tid]

===== PAGE 38 =====
Warp example 1: adding two arrays
The kernel
@wp.kernel 
def addArrays(x: wp.array(dtype=float), 
           y: wp.array(dtype=float), 
           z: wp.array(dtype=float)): 
    # thread index 
    tid = wp.tid() 
    # compute the sum 
    z[tid] = x[tid]+y[tid]
