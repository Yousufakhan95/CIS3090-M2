1. Overview 
In this assignment, you will break a simple substitution cipher by brute force and use MPI to 
spread the work across processes. The input is a batch of encrypted messages. Some 
messages are cheap to break and some are very expensive, so you need to balance the load 
and keep all the processes busy.
You will write three programs:
-encrypt: a serial program that encrypts one plaintext message (Section 2).
-decryptSerial: a serial program that decrypts a batch of messages by brute force (Section 
3). It is your prototype and your baseline for speedup.
-decryptParallel: an MPI version of decryptSerial that hands out messages to worker 
processes through a work queue (Section 4).
2. Encryption 
The cipher replaces each letter of a message with another letter from the same message. 
Plaintext messages contain only lower-case letters and single spaces, with no leading or trailing 
spaces.
To encrypt a message:
1.Build the letter set: list each distinct letter of the message in order of ﬁrst appearance. 
Spaces do not count as letters. Each unique letter must appear only once in this list.
2.Build the key: a random rearrangement of the letter set. How you randomize it is up to you, 
but make sure the letters are thoroughly mixed.
3.Replace each letter of the message with the key letter at the same position as that letter in 
the letter set. Spaces pass through unchanged.
Example:
plaintext:   the cat
letter set:  theca
key:        cehat
ciphertext:  ceh atc
The letter t is at position 0 of the letter set, so it becomes c, the key letter at position 0. 
Likewise, h becomes e, e becomes h, and so on.
The encrypt program takes the plaintext as its only command-line argument and prints the 
ciphertext to stdout, followed by a newline.

3. Decryption 
The decryption program does not know the key, so it searches for it by brute force. For each 
ciphertext message: 
1.Build the ciphertext's letter set, in order of ﬁrst appearance. For ceh atc, it is cehat.
2.Try every rearrangement of that letter set as a candidate key. To decode, replace each 
ciphertext letter with the candidate letter at the same position as that letter in the ciphertext's 
letter set.
3.If every decoded word is in the word list, the decryption is valid.
Example, for ciphertext letter set cehat:
candidate ceaht:  ceh atc  ->  cea htc   (not words: rejected)
candidate theca:  ceh atc  ->  the cat   (valid)
A message with n distinct letters has n! candidate keys: 120 for the cat, over 3.6 million for 10 
distinct letters, and almost 40 million for 11. You must try every candidate, because more than 
one key can produce a valid decryption, and you must report all of them. Generate every 
candidate key in full: do not skip keys based on a partial decryption. You may stop checking a 
candidate at its ﬁrst invalid word.
We provide the word list in the ﬁle words.txt, which contains lower-case words, one per line, 
with no duplicates. Load it into memory once and look words up there. Do not call external 
programs such as grep to check words: this would mess up your timings, since they would 
measure process creation (starting grep) rather than decryption.

4. Parallel Decryption Design 
4.1 Overview
The program decryptParallel runs in three phases: setup, work queue, wrap-up. Each 
phase uses a different kind of MPI communication. At startup, the program loads the word list 
ﬁle on rank 0 and shares it with all other ranks through explicit communication. Do not try to

read the word list directly from the disk on ranks other than 0. The manager on rank 0 reads all 
the messages from the ciphertext and gives a message to each worker that asks for it. Once all 
the workers in the communicator are busy, the manager waits. 
As workers complete their tasks, they send decrypted plaintext messages back: either every 
valid decryption, or a note that there was none. The manager gives new messages to free 
workers. This continues until there are no messages left in the ciphertext ﬁle. 
When the ﬁle is exhausted, the manager waits for the remaining results from the workers, then 
tells each worker to stop. All ranks report their statistics to rank 0 (Section 4.4) before 
terminating. Rank 0 terminates once it has received all the statistics.
4.2 Setup
Only rank 0 opens input ﬁles. On a real MPI cluster, you can’t assume that every node can see 
the input ﬁles, so reading them on one rank and distributing the contents is the safe approach. 
Rank 0 reads the word list and shares it with the workers using MPI_Bcast: ﬁrst the ﬁle size, 
then the ﬁle contents exactly as read. Each worker then builds its own local lookup structure 
from it.
Rank 0 also reads the whole ciphertext ﬁle at startup and stores it in a statically allocated 2D 
array (Section 5.2 gives the limits on message count and length). Once the ciphertext has been 
read in, rank 0 starts sending the individual messages to the workers.
4.3 Work Queue and Message Protocol
Rank 0 serves as the manager and ranks 1 to p-1 are workers. The manager does no 
decryption. A worker asks for a message, decrypts it, and returns its results with its next 
request. When the batch is empty, the manager answers each request with a termination 
message. The manager then prints all results (Section 5.3).
Use the following four message types, each identiﬁed by its tag. Deﬁne the tags as named 
constants. Their values are up to you. Use the tags in the messages to establish the purpose of 
the message, while the data buffer carries the payload.
Tag Sent by Contents
TAG_REQUEST worker one int: the number of valid decryptions that follow
TAG_RESULT worker one valid decryption, as char[256]
TAG_WORK manager one ciphertext message, as char[256]
TAG_STOP manager no data

Rules:
-A worker’s ﬁrst request for a message has a count of 0, with no results after it.
-After decrypting a message, a worker sends a request with the number of valid decryptions it 
found, followed by one TAG_RESULT message per decryption. A count of 0 means the 
message had no valid decryption.
-The manager receives a request from any worker, then receives that worker’s results from 
that worker only.
-The manager answers each request with either the next message (TAG_WORK) or, if the batch 
is empty, TAG_STOP.
-The manager is responsible for knowing which message each worker is working on.
-The manager ﬁnishes once every worker has received TAG_STOP.
References: Unlike the lecture examples, the manager doesn't know which rank it's waiting for 
with its MPI_Recv. Check the textbook Section 3.1 on how to use MPI_Recv with 
MPI_ANY_SOURCE and status.MPI_SOURCE. The use of tags in MPI communications is 
described there as well.
4.4 Wrap-up
Once all the workers have ﬁnished, the manager collects the per-rank statistics with 
MPI_Gather, one call per statistic. From the gathered busy times, the manager then ﬁnds the 
minimum and maximum across the workers (ranks 1 to p-1).
Timing: all ranks call MPI_Barrier before starting the clock, and use MPI_Reduce with 
MPI_MAX on elapsed time.
 
Every rank, including the manager, must reach these collective communication functions, or the 
program may hang.

5.3 Output Speciﬁcation
The executables decryptSerial and decryptParallel print their results to stdout, one 
line per valid decryption:
<msgIndex>: <plaintext>
Where <msgIndex> is the message’s line number in the ciphertext ﬁle, starting at 1. A 
message with more than one valid decryption prints one line for each. A message with no valid 
decryption prints:
<msgIndex>: NONE
Lines may appear in any order. When grading A2, we will sort your output before comparing it 
with ours.
The executable decryptParallel prints one statistics line per rank, from rank 0, in rank 
order:
RANK: <r> MESSAGES: <m> KEYS: <k> BUSY: <seconds>
-MESSAGES: the number of messages the rank decrypted.
-KEYS: the number of candidate keys the rank tested. This can exceed the range of an int. 
Use long instead, and MPI_LONG when gathering it.
-BUSY: the time the rank spent decrypting, not counting time spent waiting for the manager.
Rank 0’s line is all zeros. After the per-rank lines, rank 0 prints the minimum and maximum busy 
time across the workers, followed by the elapsed time:
