===== PAGE 5 =====
Distributed memory systems 
• Because the machines connected by a network are physically separated, sharing data 
between them takes time - whereas data sharing between threads is nearly instantaneous 
• As a result, distributed memory systems in general - are best suited for tasks where the 
computations are long 
• They only make sense in situations where the machines spend more time computing than 
communicating 
•
Sending data and synchronization messages over the network can take a lot of time 
•
Therefore, computing has to take even longer - otherwise we won't get much of a speedup 
• This is a particularly good fit for data-parallel problems
5

===== PAGE 6 =====
Applications of distributed memory systems
• E.g. a render farm: 
•
You need to create high-quality 3D animation 
•
Each animation might take a long time - e.g. a minute for a scene with a very high poly count, 
complex realistic lighting, and high resolution 
• Each frame gets rendered on a separate physical machine 
•
3D scene data for each new frame get transferred to each machine after it finished rendering an 
old frame 
•
We could also batch this to optimize communications overhead, and send a set of frames to 
each physical machine 
• The frames get stitched into a video once (or as) they are completed
6

===== PAGE 7 =====
MPI 
• The MPI - Message Passing Interface - library is used for writing parallel code on distributed 
memory systems.  
• It allows you to send and receive messages between processes 
• MPI has historically been used with network-connected clusters of computers - each with its 
own cores and memory 
•
E.g. various supercomputing clusters 
• The processes can be on different physical machines, or on the same one, or even a 
combination of both - MPI abstracts that away for us 
•
E.g. 100 networked workstations with 8 cores each, capable of running 800 processes in 
parallel
7

===== PAGE 8 =====
MPI vs pthreads
• Pthreads  
•
assumes shared memory 
•
works with threads 
•
designed for concurrency, rather than parallel computations, so does not have any tools for 
helping parallel computations - we do everything ourselves, manually 
• MPI  
•
assumes distributed memory  
•
works with processes 
•
designed with parallel computation in mind 
• We will review MPI examples and in the process learn how it can help us do parallel 
computations

===== PAGE 9 =====
MPI - the Message Passing Interface
• MPI is, as its name suggests, designed around passing of messages as the means of inter-
process communication 
• All processes are running the same code 
• No sharing, so the data that each process has to work on must be explicitly sent to the process 
•
If you are 100% certain that all the processes work on the same physical machine, they have 
access to the shared disk 
•
However, for real-world systems that use MPI, this is not the case - they are separate systems on 
the same local network 
• This imposes a high data transfer cost on the parallelized code, which didn't exist in the shared 
memory examples with Pthreads
9

===== PAGE 11 =====
MPI - the Message Passing Interface
Communication between multiple entities
• Additional operations exist for 1-to-N, N-to-1, and N-to-N communications 
• Broadcast - send the same data to multiple processes (1-to-N) 
• Reduction - send the individual data from multiple processes to one, possibly combining 
data using the specified operation (N-to-1)  
• Butterfly reduce, which MPI calls "all reduce" (N-to-N) 
•
send the individual data from multiple processes to one, possibly combining data using the 
specified operation (N-to-1) 
•
send the combined result back to all the processes  (1-to-N)

===== PAGE 28 =====
MPI components 
• A communicator is a set of processes that send messages to each other. In the previous 
example the communicator was MPI_COMM_WORLD.  
•
The communicator lets you access information about the set of processes - think of it as a 
communication channel 
• Complex programs use communicators to control which processes can interact.  
•
They limit which processes can communicate so unnecessary messages aren’t received and to 
prevent messages from being accidentally received.  
• Processes are identified by rank (think of it as a relative process ID) 
• Processes send and receive messages to other processes in the same communicator, using 
the rank to identify the expected receiver or sender in 1-to-1 communications
28

===== PAGE 29 =====
MPI_Send() 
Basic function for synchronous sends
• MPI_Send(const void* buf, int count, MPI_Datatype datatype,  
	
	
   int dest, int tag, MPI_Comm comm);  
•
buf is the pointer to memory (array) containing the message 
•
count is the length of the message - the number of things  
•
datatype is the macro indicating the type being sent 
•
dest is the rank of the process destination (the receiver of the message).  
•
tag is a non-negative int which is used to distinguish between messages. 
•
comm is the communicator -  identifies which processes should be able to access the message 
• See textbook and online MPI docs for more details

===== PAGE 31 =====
MPI_Recv() 
Basic function for synchronous receive
• int MPI_Recv(void* buf, int count, MPI_Datatype datatype,  
              int source, int tag, MPI_Comm comm, MPI_Status* status) 
•
The first six arguments of MPI_Recv() are the same as MPI_Send().  
•
All parameters are specified by the caller in the MPI_Recv() call, except &status 
•
In other words, you need to know the size, type, source, and communicator for the message 
being received - which might be a bit unexpected 
•
This means that the message passing patterns in MPI applications must be carefully thought 
through 
•
status is information about the message. Can be stored in a pointer or ignored 
• See textbook and online MPI docs for more details

===== PAGE 34 =====
MPI send and receive operations
• MPI_Send() can either: 
•
buffer the message - store the message to be transmitted and return to the program  
•
block - wait until the message is sent to return to the program  
• With buffering, you don’t know if the message has been transmitted after a send.  
• This behaviour is implementation dependent.
34

===== PAGE 35 =====
MPI send and receive operations
• MPI_Recv() always blocks until a message is received. 
• There are different send and receive functions which are non-blocking: MPI_Isend() and 
MPI_Irecv() 
• Messages are nonovertaking.  
•
This means the order that messages are sent from one process will not change. 
• The order of messages from multiple processes is not enforced. 
35

===== PAGE 36 =====
Problems due to blocking
• A receive with no send will hang (block forever)  
• If tags or ranks do not match then the receive will not match the send 
•
In this case the process may hang or may match the wrong send  
• If a send blocks waiting for a receive then it can hang 
• If a send buffers and there is no receive then the message is lost 
36

===== PAGE 37 =====
MPI input and output
• The MPI standard does not describe access to I/O devices. 
• Most implementations allow all processes to write to stdout and stderr.  
• The order of output is unpredictable. 
• Multiple process outputs can appear in any order or interrupt each other.  
• Output is nondeterministic. 
37

MPI input and output
• Only process 0 in MPI_COMM_WORLD can access stdin. 
• If data is read from stdin then process 0 must send it to other processes.

void Get_input(int my_rank, int comm_sz, double* a_p, double* b_p, int* n_p) {  
	
int dest;  
	
if (my_rank == 0) {  
	
	
printf("Enter a, b, and n\n"); 
	
	
scanf("%lf %lf %d", a_p, b_p, n_p); 
 
	
	
for (dest = 1; dest < comm_sz; dest++) {  
	
	
	
MPI_Send(a_p, 1, MPI_DOUBLE, dest, 0, MPI_COMM_WORLD);  
	
	
	
MPI_Send(b_p, 1, MPI_DOUBLE, dest, 0, MPI_COMM_WORLD);  
	
	
	
MPI_Send(n_p, 1, MPI_INT, dest, 0, MPI_COMM_WORLD);  
	
	
} 
 
	
} else { /* my_rank != 0 */  
	
	
MPI_Recv(a_p, 1, MPI_DOUBLE, 0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);  
	
	
MPI_Recv(b_p, 1, MPI_DOUBLE, 0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);  
	
	
MPI_Recv(n_p, 1, MPI_INT, 0, 0, MPI_COMM_WORLD, MPI_STATUS_IGNORE);  
	
} 
} /* Get_input */
